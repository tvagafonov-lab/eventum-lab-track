# ПУЛЬТ — панель управления программным продуктом

Концепция оболочки, которая делает любую программу видимой как схему n8n:
модули-блоки, соединители, свойства по клику, переменные — и всё это агент
обязан вести параллельно разработке, начиная со стадии спецификации.

Статус: концепт + рабочий прототип (этот каталог). Дата: 2026-08-30.

---

## 1. Задача

Программы, которые мы создаём, по сути — наборы модулей, выполняющихся
последовательно и по условиям. Но традиционная кодовая база это скрывает:
чтобы понять, «что вообще делает программа и куда идёт разработка», нужно
читать файлы. Визуальные конструкторы (make.com, n8n, конструкторы ботов)
решают это радикально — схема и есть документация — но заставляют жить
внутри своего конструктора.

Пульт берёт от них только отображение, не способ разработки:

- программа разрабатывается привычно, обычными файлами;
- параллельно — в безусловном режиме — агент ведёт **карту продукта**;
- карта рендерится в **панель**: блоки-модули с соединителями, клик по
  блоку открывает свойства (описание, файлы, переменные, связи);
- часть переменных можно менять прямо из панели, часть — только кодом;
- панель — не конструктор: связи в ней не настраиваются, это визуальная
  схема программы с настройкой только переменных;
- на этапе спецификации карта — костяк будущей программы: сразу видно,
  что агент понял правильно, а что нет;
- при отладке карта отвечает на вопрос «где это происходит и какими
  файлами» без чтения кода.

## 2. Что уже существует (обзор, август 2026)

Смотрел на четыре класса решений.

**Канвы и workflow-редакторы.** n8n, Node-RED, make.com — источник языка
отображения: блок, порт, bezier-соединитель, панель свойств справа,
условные ветки. Библиотеки для таких канв: React Flow (доминирует,
~1.1 млн скачиваний/нед), Rete.js, Drawflow, LiteGraph.js. Всё это —
редакторы исполняемых графов: граф и есть программа. Нам нужно обратное —
граф как зеркало обычной программы.

**Architecture-as-code.** LikeC4 (likec4.dev) — ближайший по философии:
модель архитектуры в DSL-файлах в репозитории, из неё — живые
интерактивные диаграммы; «код — единственный источник правды». Структуризация
уровней взята оттуда и из C4/Structurizr. Чего нет: переменных продукта,
статусов разработки, файлового маппинга «модуль ↔ файлы», контракта
с агентом. Backstage (Spotify) — та же идея каталога через
`catalog-info.yaml` + граф зависимостей, но это тяжёлый корпоративный
портал, не файл в репо.

**Агентские карты кодовых баз.** Весна 2026 сделала это мейнстримом.
Understand-Anything (~40 тыс. звёзд, №1 в трендах в мае) — плагин Claude
Code: мультиагентный анализ строит граф знаний файлов/функций/зависимостей
в `.ua/knowledge-graph.json` прямо в репозитории, поверх — интерактивный
дашборд (нужен Node-сервер), обновление инкрементальное, есть post-commit
хук `--auto-update`. codegraph (~54 тыс. звёзд) — локальный граф кода для
агентов: fs-watcher переиндексирует при каждом изменении, агент ходит
в граф через MCP (`codegraph_explore` с call paths и blast radius),
конфиг-файл `codegraph.json` коммитится в репо; дашборда для человека нет.
CodeBoarding — каталог `.codeboarding/`: `analysis.json` + markdown +
mermaid, инкрементальность через `fingerprint.json`, GitHub Action.
Archify (~20 тыс. звёзд) — agent-skill: самодостаточный интерактивный HTML
с диаграммами, узлы со ссылками на строки кода («evidence»). Сюда же
авто-визуализаторы: gitdiagram (репо → кликабельная диаграмма, клик
открывает файл), DeepWiki (репо → вики с диаграммами), Swark (VS Code +
Copilot → mermaid), ReposLens. Всё это — **производная документация**:
снизу вверх, «что агент увидел в коде», без статусов разработки,
переменных, приёмки и стадии спецификации. Пульт — **контракт**: сверху
вниз, «что продукт обязан собой представлять», и код сверяется с картой,
а не наоборот. Важно: эти два слоя не конкурируют — граф кода может
питать наш doctor (см. дорожную карту).

**Living documentation.** Заметная волна текстов и продуктов про
«архитектура в YAML в git, диаграммы генерируются, агент ловит дрейф
кода от документа» — например, Archyl (SaaS, судя по блогу: drift
detection, conformance, maturity score; сайт из этой среды недоступен,
оценка по описаниям) и шаблон Living Architecture (architecture.md
для агентов, 10 разделов, три уровня глубины). Подтверждает спрос
именно на контрактный слой, но всё это — текст или диаграммы для
архитекторов, не пульт продукта с переменными.

Отдельно — рендер-скиллы: architecture-diagram-skill делает из описания
один самодостаточный HTML с анимированными потоками данных, side panel
со свойствами шага и переключателями режимов. Одноразовая генерация без
привязки к файлам репозитория, но подтверждает выбранную нами форму
(один HTML, боковая панель, потоковая анимация).

**Spec-driven development.** GitHub Spec Kit, OpenSpec, Kiro, BMAD —
волна 2025–2026: спецификация как первичный артефакт, код — производная.
Совпадает с нашей фазой «сначала костяк со спецификациями». Но всё это
текст: спека не превращается в живую панель продукта и умирает после
имплементации (архивируется). У нас карта живёт всю жизнь продукта.

**Вывод.** Ниша по-прежнему свободна: никто не совмещает
(а) манифест-контракт в репозитории,
(б) n8n-подобную панель со свойствами и переменными,
(в) обязательный цикл агента «прочитай карту → работай → обнови карту
и changelog»,
(г) приёмку человеком (verified) и работу со стадии спецификации.
Каждый кусок существует и проверен — вплоть до десятков тысяч звёзд
у соседей по нижнему слою — значит, собирается из готовых идей без
исследовательского риска, а спрос на класс инструментов подтверждён
рынком.

## 3. Устройство Пульта

Пять составляющих, все живут в репозитории продукта:

```
репозиторий продукта
├── PRODUCT.md            ← описание программы (обязательное чтение агента)
├── CHANGELOG.md          ← журнал изменений (обязательное чтение + запись)
├── CLAUDE.md             ← + вставка-контракт (см. skill/templates/)
└── pult/
    ├── product.yaml      ← КАРТА: манифест продукта (источник правды)
    ├── panel.html        ← ПАНЕЛЬ: генерируется из карты, руками не правится
    └── tools/embed.py    ← генератор: вшивает карту в панель
```

**Карта** (`product.yaml`, формат — в SCHEMA.md): паспорт продукта, модули
двух видов (`pipeline` — конвейер, `service` — служебные), связи `flows`
(с условиями `when` — это условное выполнение), связи `uses`
(модуль → служебный), общие файлы `shared`, у каждого модуля — файлы
с ролями (owner/part/reads) и переменные с признаком `edit: panel|code`.

**Панель** (`panel.html`) — один самодостаточный файл, без сборки
и без сервера: открывается локально двойным кликом, с GitHub Pages,
публикуется артефактом Claude. Слева канва в языке n8n: конвейер слева
направо, условные рёбра пунктиром с подписью условия, служебные модули
в отдельной нижней полосе, блок «Общие файлы». Клик по блоку — справа
свойства: Обзор / Файлы / Переменные / Связи.

**Контракт агента** — вставка в CLAUDE.md продукта + скилл `pult`
(skill/SKILL.md). Суть контракта:

1. Перед работой над продуктом агент читает PRODUCT.md, CHANGELOG.md
   и pult/product.yaml (вдруг человек поменял свойства или переменные).
2. После любого значимого изменения кода агент безусловно обновляет карту
   (новый модуль, файлы, переменные, статусы), пишет строку в CHANGELOG.md
   и перегенерирует панель. Не по просьбе — всегда.
3. Агент никогда сам не ставит `verified: true` — это подпись человека.

**Признак `verified`** — механизм «что агент понял правильно, а что нет».
Всё, что агент реконструировал или спроектировал сам, помечено
`verified: false` и видно на панели знаком «?». Владелец просматривает
схему, говорит «радар описан верно» — агент снимает знак. На этапе
спецификации вся карта состоит из «?» — и это честная картина.

**Черновик изменений** — редактирование переменных. Панель статическая,
писать в репозиторий сама не может (v1 — осознанно). Переменные
с `edit: panel` редактируются в интерфейсе, изменения копятся в «черновик»
(живёт в localStorage), кнопка формирует готовое задание для агента:
что поменять, где лежит, что обновить после. Человек вставляет это
в чат — агент применяет, синхронизирует карту, панель и changelog.
Переменные с `edit: code` показываются с замком и адресом в коде.

## 4. Жизненный цикл

**init (этап спецификации).** Продукта ещё нет. Агент вместе с человеком
собирает карту-костяк: модули со статусом `spec`, связи, будущие
переменные, всё `verified: false`. Панель уже работает — по ней видно,
куда пойдёт разработка, и ошибки понимания ловятся до кода.

**sync (параллельно разработке, безусловно).** Каждое изменение кода
отражается в карте: статусы `spec → build → ready`, реальные файлы,
реальные переменные и их текущие значения. CHANGELOG.md растёт. Панель
перегенерируется тем же коммитом.

**doctor (профилактика дрейфа).** Периодическая сверка карты с кодом:
файлы карты существуют? появились файлы-сироты вне карты? переменные
на месте и значения совпадают? данные панели не разошлись с картой?
Отчёт — человеку, решения — за ним.

**verify (приёмка человеком).** Владелец смотрит панель, подтверждает
или исправляет блоки; агент переносит подпись в карту.

## 5. Решения и компромиссы

- **YAML-манифест, не DSL.** LikeC4-подобный DSL выразительнее, но YAML
  агент пишет и правит надёжнее, диффы читаемы, парсится чем угодно.
- **Один HTML-файл, ноль зависимостей.** Никакого React Flow: панель
  читает JSON, раскладывает конвейер сама (топологические ранги слева
  направо) и рисует SVG-рёбра. Нет сборки — нет порога входа: панель
  выживает в любом репо и любом окружении.
- **Данные вшиваются в панель** (между маркерами `PULT:DATA`), а не
  грузятся fetch'ем: файл работает и с диска, и как артефакт, и на Pages.
- **Раскладка автоматическая.** Агент не думает о координатах; ручной
  `position` — опция для капризных случаев.
- **Панель ничего не пишет.** Запись в репозиторий — только через агента.
  Это не ограничение прототипа, а граница ответственности: источник
  правды один, и меняет его тот, кто отвечает за согласованность.
- **Секреты в карту не попадают** — только факт существования переменной
  и адрес её настоящего дома.

## 6. Куда это натягивается

Карта в этом каталоге — **Eventum Lab**, реконструированный по витрине
track record (потому и почти весь в «?»). Прицел дальше:

- **cbsf automation** — конвейер + классический служебный Telegram-модуль;
- **Соня и Володя** — ролевое взаимодействие двух агентов читается
  как схема с двумя дорожками;
- **Электрогалина** — то же самое.

Для каждого продукта — свой `pult/` в его репозитории; скилл один на всех.

## 7. Дорожная карта

1. **v1 (этот прототип):** формат карты, панель, скилл-контракт, черновик
   изменений переменных.
2. **v1.1:** doctor как строгая процедура скилла; сверка «карта ↔ реальные
   импорты» (по языкам: сначала Python/JS через grep импортов). Если
   в проекте стоит Understand-Anything или codegraph — doctor берёт
   реальный граф из их индексов (`.ua/knowledge-graph.json`, MCP
   codegraph) вместо собственного grep: нижний слой «что в коде»
   у них уже решён, наш слой — сверка с контрактом.
3. **v1.2:** перенос скилла в общую скилл-инфраструктуру (каталог Skiller),
   шаблон SessionStart-хука, который сам подсовывает агенту PRODUCT.md +
   CHANGELOG.md + карту в начале сессии.
4. **v2 (запись из панели):** варианты — коммит через GitHub API с токеном
   владельца; или панель как артефакт Claude с сохранением состояния,
   которое агент забирает при следующей сессии. Оба требуют решения
   о хранении токена/доверии — отдельный разговор.
5. **v2.x:** история карты поверх git (слайдер «как выглядел продукт
   месяц назад»); мультипродуктовый «пульт пультов» — один экран со всеми
   продуктами и их статусами.

## 8. Открытые вопросы (владельцу)

1. Имя. Рабочее — «Пульт» (каталог `pult/`). Живёт?
2. Правильный ли состав вкладок свойств: Обзор / Файлы / Переменные / Связи?
3. v2-механику записи переменных из панели делать через GitHub API
   (токен в панели) или через артефакт с состоянием (агент забирает)?
4. Нужен ли отдельный статус «служебный, но выключен» для модулей вроде
   резервных каналов?
5. Порог «значимого изменения» для безусловного sync: любое изменение
   поведения/файлов/переменных модуля — так?
