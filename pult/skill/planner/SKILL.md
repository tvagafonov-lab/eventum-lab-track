# pult-planner — спецификации и детальный план разработки

Работает ПОВЕРХ карты `pult/product.yaml`: замысел пишет в `spec` модулей,
архитектуру — в `files` и `standards`, план — в `plan[].stages[]`.
Исполнители получают самодостаточные контекст-пакеты и не видят ничего
лишнего. Формат полей — `pult/SCHEMA.md`.

## Семь принципов (и откуда взяты)

1. **Контекст-бюджет прежде всего** (GSD). Этап обязан помещаться
   в свежий чат: контекст-пакет ≤ ~30–40k токенов, ожидаемая работа
   этапа — не больше половины окна исполнителя. Не влезает — дели этап,
   а не ужимай пакет.
2. **Сложность → дробление** (Taskmaster). Оцени сложность этапа 1–5;
   всё, что ≥4, дели до тех пор, пока каждый кусок ≤3.
3. **Самодостаточный этап** (BMAD story-файлы). Исполнитель ничего
   не ищет и не переспрашивает: срез карты, стандарты, имена, критерии
   приёмки — всё в пакете.
4. **Имена до кода** (Spec Kit data-model/contracts). Сущности,
   интерфейсы, ключевые переменные и файлы именуются на этапе
   архитектуры и попадают в реестр `standards.registry`. Исполнитель
   не выдумывает имена — новые предлагает в отчёте.
5. **Дельта, не переписывание** (OpenSpec). Для живого продукта пишется
   спека изменения; исторический замысел модулей не переписывается.
6. **Ворота** (approvals из spec-workflow-mcp). Спека и нарезка этапов
   уходят в работу только после подтверждения владельцем (verified);
   до подписи — это черновик планировщика со знаком «?».
7. **Модель по сложности, усилие по цене ошибки** (wshobson + матрица
   ниже). Дешёвая модель на механику, дорогая — на архитектуру
   и спутанные баги. Планирование само по себе токенов не жжёт:
   субагентов запускает владелец, не планировщик.

## Фазы

### draft — спецификация

Вход: идея, ТЗ или запрос на изменение. Выход: `spec` модулей
(новые модули создаются со `status: spec`, `verified: false`), эскиз
`flows`/`uses`, обновлённый PRODUCT.md (конституция продукта: что это,
принципы, границы). Правила:
- До 5 вопросов на прояснение ДО планирования (как Spec Kit clarify);
  всё, что осталось неясным, — в спеку с пометкой «TBD», не выдумывать.
- Для существующего продукта — дельта: спека описывает изменение,
  затрагиваемые модули перечисляются явно.

### architect — файловая архитектура и имена

Выход: `files` модулей (пути будущих файлов — до кода), `standards`
(конвенции имён, пороги размеров), `standards.registry` — реестр
ключевых имён: сущности, интерфейсы, ключи конфигов, интерфейсные
файлы; каждому — `location`. Переменные-кандидаты — в `variables`
модулей с `edit: panel|code`. Правила:
- Один модуль — один каталог; файл при рождении получает назначение
  (role: owner) и бюджет размера.
- Реестр — источник правды об именах: аудит потом сверяет код с ним.

### stage — нарезка плана

Выход: `plan[].stages[]`. Каждый этап:

```yaml
stages:
  - id: p7.2            # id пункта плана + порядковый
    title: "..."
    state: todo          # todo | doing | done | dropped
    role: executor       # researcher | planner | executor | verifier | auditor
    model: sonnet        # haiku | sonnet | opus | fable (алиасы Claude Code)
    effort: high         # low | medium | high | xhigh | max
    parallel: false      # можно гнать параллельно с соседями (ccpm)
    needs: [p7.1]        # зависимости-этапы
    gives: "что сдаёт: файлы/поведение — критерий приёмки одной строкой"
```

Правила нарезки:
- Бюджет и сложность — принципы 1–2. Этап касается файлов одного
  модуля; межмодульный шов — отдельный этап с ролью executor и явным
  контрактом из реестра.
- `parallel: true` только если этапы не делят файлы (по ccpm).
- Первый этап крупного пункта — researcher (инвентаризация фактов),
  последний — verifier. Цепочки длиннее 7 этапов — признак, что пункт
  плана надо делить.

### handoff — контекст-пакет этапа

По запросу владельца собери пакет для чата-исполнителя (текстом в чат
или файлом `pult/handoff/<stage-id>.md` — файл одноразовый, после
исполнения удаляется):

```
# Этап {id}: {title}
Роль: {role} · модель: {model} · усилие: {effort}

## Продукт (3–5 строк из PRODUCT.md)
## Стандарты (выжимка standards: нейминг, пороги размеров)
## Срез карты: модули этапа (spec + files + variables)
## Имена из реестра, относящиеся к этапу
## Задача и критерии приёмки (gives)
## Запрещено
- менять файлы вне среза этапа;
- вводить имена мимо реестра (новые — предложить в отчёте);
- секреты в код и в отчёт.
## По завершении
Отчёт: что сделано, файлы, новые/изменённые имена, вопросы.
Владелец передаёт отчёт агенту продукта → скилл pult: sync + changelog.
```

### audit — санация и сверка

**До кода** (после stage, перед исполнением):
1. Ссылочная целостность: этапы ссылаются на существующие модули/этапы;
   каждый пункт спеки покрыт хотя бы одним этапом; висячих этапов нет.
2. Реестр: имена уникальны, соответствуют конвенции standards.naming.
3. Бюджеты: у каждого этапа сложность ≤3 и пакет влезает в бюджет.
4. Стоимость: посчитай этапы × модели, предупреди владельца при
   больших цепочках (>10 этапов) до старта.

**После кода** (интегрируется с doctor скилла pult):
5. Deliverables этапа (`gives`) на месте; state этапов обновлён.
6. Дрейф имён: registry ↔ код (имена существуют по location, не
   переименованы молча). Расхождение — в `drift` модуля, знак «⚠».
7. Размеры файлов против standards.file_size; превышение hard-порога —
   в отчёт (делить при ближайшей правке, не механически).

## Матрица «роль → модель → усилие» (по умолчанию)

| Роль | Модель | Усилие | Для чего |
|---|---|---|---|
| researcher | haiku | low | инвентаризация, чтение доков, сбор фактов |
| executor | sonnet | medium–high | типовой этап кода по готовому пакету |
| executor (сложный) | opus | xhigh | миграции, спутанная логика, безопасность |
| verifier | sonnet | medium | приёмка этапа против критериев `gives` |
| auditor | opus | high | аудит согласованности, санация, поиск ошибок |
| planner (сам скилл) | opus | high–xhigh | спека, архитектура, нарезка |
| — особые случаи | fable | max | клубки багов, ключевые архитектурные развилки — только по явному слову владельца (дороже) |

Планировщик записывает в этап рекомендацию; финальный выбор модели —
за владельцем при запуске.

## Пороги размеров (дефолты standards.file_size)

- `soft_max_lines: 300` — цель; `hard_max_lines: 500` — при превышении
  файл делится при ближайшей правке (не механически в отдельном коммите).
- Обоснование: файл должен читаться исполнителем одним Read и оставлять
  окно для мышления; половина контекст-бюджета этапа — потолок на чтение.
- Исключения: сгенерированные файлы, данные, конфиги (перечислить
  в standards явно). Модуль толще 5–7 файлов — кандидат на разделение.

## Границы

- Не запускает субагентов и не исполняет этапы — планирует; исполнение
  стартует владелец (вручную или явной командой).
- Не ставит `verified: true` и не снимает «?»/«⚠».
- Не трогает слой факта карты (summary/details/status) — это pult sync.
- Секреты в спеки, реестр и пакеты не попадают никогда.
